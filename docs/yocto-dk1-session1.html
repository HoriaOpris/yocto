Your three questions

What is the SDK?

A toolkit installed on the VM in ~/sdk/dk1. It contains a cross-compiler: it runs on the VM but produces programs for the board's ARM Cortex-A7. It also contains a copy of the board's headers and libraries, so your program is built against exactly what the board has. The SDK itself never goes on the board.

SDK or flashed image: what's the difference?

The image is the board's whole system: bootloaders, kernel and root filesystem, written onto the SD card. The SDK is the tool you use on the VM to build programs for that system. Both came out of the same Yocto build, which is why they match. ledblink is a third thing: a program you built with the SDK and copied onto the running board.

Does make flash the board, or build on it?

Neither. make compiles on the VM. make run then copies only the finished program to the board with scp and starts it with ssh. The source code stays on the VM, and the board has no compiler. Nothing is flashed either: flashing rewrites the whole SD card, while scp adds one file.

Two ways software reaches the board

Everything starts on the VM. There are two routes to the board: a slow one you rarely use, which replaces everything, and a fast one you use every time you change your code.

The SDK in more detail

Your VM and the board use different processors. The VM is 64-bit ARM (aarch64, running on your Mac). The board's Cortex-A7 is 32-bit ARMv7. A program compiled by Ubuntu's own gcc would only run on the VM. Compiling on one machine for a different one is called cross-compiling, and the SDK is what makes it work.

Installing the SDK unpacked three things into ~/sdk/dk1:

# the compiler, linker and tools: they run on the VM
sysroots/aarch64-pokysdk-linux/
# a copy of the board's headers and libraries (glibc etc.), same versions as the image
sysroots/cortexa7t2hf-neon-vfpv4-poky-linux-gnueabi/
# a script that points everything at the two folders above
environment-setup-cortexa7t2hf-neon-vfpv4-poky-linux-gnueabi

Running source on that script only changes settings in the current terminal. The key one is $CC, which is what make uses to compile:

CC=arm-poky-linux-gnueabi-gcc -mthumb -mfpu=neon-vfpv4 -mfloat-abi=hard \
   -mcpu=cortex-a7 ... --sysroot=/home/horia/sdk/dk1/sysroots/cortexa7t2hf-...

-mcpu=cortex-a7 tells the compiler which processor to generate code for. --sysroot makes it use the board's copy of the headers and libraries instead of the VM's. That's why the SDK has to come from the same build as the image: if the libraries didn't match, programs could fail to start on the board.

What make run does, step by step

The Makefile chains three targets: run needs deploy, and deploy needs the ledblink binary. make only recompiles if ledblink.c changed since the last build.

VM · build

Compile. The SDK's cross-compiler turns the source into an ARM program. This happens entirely on the VM.

arm-poky-linux-gnueabi-gcc ... ledblink.c -o ledblink
# result: ELF 32-bit LSB pie executable, ARM
VM → board

Copy. scp sends the compiled binary, not the source, to root's home folder on the board. dk1 is the SSH alias for root@192.168.0.19.

scp ledblink dk1:
Board · run

Run. ssh starts the program on the board. Its output comes back over the network to your VS Code terminal, so it looks local, but it runs on the Cortex-A7.

ssh dk1 ./ledblink 200 10

Copying is not flashing. Flashing writes a whole image over the SD card, replacing the bootloaders, kernel and every file. scp adds one file to the running system and leaves everything else alone. That's why the edit–compile–run loop takes seconds, not hours.

Next: ship ledblink inside the image

Right now ledblink only exists until the next reflash. The Yocto way to make it permanent is a recipe in your own layer, meta-mydk1. A recipe is a short file telling bitbake where the source is and how to build and install it. Bitbake then builds the program the same way the SDK does and puts it at /usr/bin/ledblink in every image. The Makefile already has the install target the recipe will use. It's also a good point to move the DK1 settings out of local.conf into that layer.
